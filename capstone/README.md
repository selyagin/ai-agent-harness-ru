# Capstone: безопасный CLI agent harness

Финальный проект курса: минимальный TypeScript CLI, который демонстрирует ключевые части безопасного coding-agent harness без подключения к модели. Он показывает, где должны находиться границы доверия: инструкции проекта, ограниченные инструменты, решение о подтверждении и выполнение в рабочем каталоге.

## Что умеет пример

- Загружает проектные инструкции из `AGENTS.md`.
- Формирует system prompt с задачей и контекстом проекта.
- Читает только относительные пути внутри текущей рабочей директории.
- Блокирует типичные файлы секретов: `.env`, `*.pem`, `*.key`, `*.p12`.
- Ищет текст через `git grep` и обрезает чрезмерно длинный вывод.
- Оценивает команды как `allow`, `ask` или `deny`.
- Исполняет только allowlisted-бинарники (`git`, `npm`, `node`) и только после policy-проверки.

## Установка

```bash
cd capstone
npm install
```

## Запуск

Запустите пример из папки `capstone`, чтобы `AGENTS.md` считался инструкцией текущего проекта:

```bash
npm run dev -- --task "Найди реализацию sandbox" --query "LocalSandbox" --read "src/sandbox.ts"
```

Проверка без изменения состояния:

```bash
npm run dev -- --task "Проверь статус репозитория" --command "git status --short"
```

Команда, требующая подтверждения, не будет выполнена автоматически:

```bash
npm run dev -- --task "Установи пакет" --command "npm install zod"
```

А опасная команда будет запрещена policy-слоем:

```bash
npm run dev -- --task "Удалить файлы" --command "rm -rf tmp"
```

## Ограничения

Этот проект — учебный harness, а не production sandbox. Проверка регулярными выражениями и allowlist не заменяют изоляцию операционной системы. Для реального агента добавьте контейнер или VM, отдельного непривилегированного пользователя, read-only mounts, отключенную сеть по умолчанию, лимиты CPU/RAM/времени, аудит действий и независимую проверку диффа перед применением изменений.

## Как развивать

1. Добавьте адаптер модели, который может выбирать только типизированные `ToolCall`.
2. Храните журнал решений policy и результатов инструментов.
3. Реализуйте отдельный UX-поток подтверждения для `ask`.
4. Добавьте тесты на обход путей, секреты и запрещенные команды.
5. Выполняйте изменения в отдельной ветке или временной копии репозитория, а не в рабочей директории пользователя.
